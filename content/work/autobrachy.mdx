The first fully automated cervical cancer brachytherapy treatment planning system — reducing manual planning workload by 80% and enabling faster, more consistent patient treatment across hospitals nationwide.

## The Problem

Cervical cancer brachytherapy treatment planning is one of the most demanding workflows in radiation therapy. A medical physicist manually positions virtual radiation sources inside a 3D anatomical model, then iteratively adjusts dwell times to maximize tumor coverage while protecting surrounding organs — the bladder, rectum, and sigmoid colon. Each plan takes hours. Quality varies significantly between planners. And timing matters: delays in planning directly delay patient treatment, which affects outcomes.

AutoBrachy automates this entirely. The clinician selects imaging, chooses an applicator type, and receives an optimized treatment plan in minutes.

## Impact

- **80% reduction** in manual treatment planning workload
- **Beta-tested and validated** with 3+ leading hospitals
- **Faster planning** supports timely brachytherapy completion — clinically associated with better survival outcomes for cervical cancer

## My Role

Full-stack engineer across the Django backend data pipeline and Angular frontend. The algorithm engineer owned the GPU optimization logic; I owned everything around it — getting data in, processing results, and surfacing them to clinicians.

**Team:** 1 algorithm engineer · 1 clinical researcher · me

## Backend: Dose Data Pipeline

### Planning workflow integration

I built the backend layer connecting the clinical interface to the GPU algorithm: retrieving patient imaging and RT Structure Sets from Orthanc, loading machine and applicator configurations (including source decay corrections by calibration date), serializing the full planning context, invoking the algorithm subprocess, and receiving the resulting RT Dose and RT Plan DICOM files. After the algorithm runs, I built the upload pipeline that pushes results back to Orthanc — immediately accessible to the frontend and the hospital's broader imaging infrastructure.

### Dose loading and NIfTI caching

RT Dose files are 3D voxel grids expensive to reprocess on every request. I built the module that loads them via pydicom, converts to NIfTI, and caches at the application layer. I also built the isodose contour generation pipeline — extracting dose boundaries at clinically relevant levels (prescription dose, 50%, 200%) for overlay rendering on CT images.

## Frontend: Clinical Visualization

### Dose overlay viewer

Isodose contour lines rendered over CT images in synchronized multi-viewport display (axial, sagittal, coronal), letting clinicians evaluate spatial dose distribution relative to tumor and organs at risk.

### Dose-volume histogram (DVH)

The primary tool clinicians use to judge plan quality. Cross-references the 3D dose grid against organ structure contours; built with Chart.js.

### Cumulative dose tracking

Brachytherapy is delivered across 3–5 fractions over ~2 weeks. I built the interface that tracks total dose accumulation across fractions — including prior external beam radiation — and flags when cumulative exposure approaches organ tolerance limits.

### Settings management

Machine configurations, applicator parameters, and source decay corrections, with role-based access so hospital physicists only see their own deployment.

## Closing reflection

Owning both ends of the algorithm handoff — data in and results out — plus the full visualization layer meant I could optimize the pipeline end-to-end. The dose caching layer made visualization feel instant. The clean serialization boundary made the algorithm independently testable. The interface only works because the data behind it is fast and correct.
