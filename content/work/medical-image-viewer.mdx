## A Ceiling, Not Just a Bug

The existing viewer used Cornerstone.js — the original library, now superseded — which rendered each image slice independently as a 2D entity. Three orthogonal viewports each maintained their own data, their own coordinate space, their own state. The limitations weren't quirks to work around. They were architectural:

- No shared volume → 3D segmentation was structurally impossible
- Per-slice rendering → redundant GPU work; no texture atlas management
- Legacy Angular coupling → blocked every modern dependency
- Main-thread paint operations → frame drops on large clinical volumes

No amount of optimization fixes a ceiling. The right call was a full migration to Cornerstone3D — and I proposed it, evaluated the alternatives, and led the execution.

        NIfTI Spacing Error in Cornerstone3D
      </h3>
      <div className="text-sm text-gray-600">Coronal and sagittal volumes rendered visually squished. Axial views were fine, masking the problem in most testing.</div>
    </div>

<StepCard number={1} title="Check our own pipeline first">
  NIfTI generation, affine headers, spacing values — all validated correct. The
  bug wasn't ours.
</StepCard>

<StepCard number={2} title="Check Cornerstone3D's functions individually">
  Affine parsing: correct. Spacing calculation: correct. Every component looked
  fine in isolation.
</StepCard>

<StepCard number={3} title="Change approach: trace the data flow end-to-end">
  Stopped checking functions in isolation. Traced from the first line of the
  NIfTI loader to the volume constructor. Found it in the translation layer
  between modules.
</StepCard>

<StepCard number={4} title="Root cause" highlight>
  The loader multiplied each direction vector component by its corresponding
  axis spacing (spacing[0], spacing[1], spacing[2]) instead of slice spacing
  (spacing[2]) uniformly. For axial scans with direction vector [0,0,1], the
  zeros masked the error. Only non-Z orientations exposed it.
</StepCard>

<CodeDiff before={[
  "pos[x] = origin[x] + k × direction[6] × spacing[0]   ← wrong",
  "pos[y] = origin[y] + k × direction[7] × spacing[1]   ← wrong",
]} after={[
  "pos[x] = origin[x] + k × direction[6] × spacing[2]   ← correct",
  "pos[y] = origin[y] + k × direction[7] × spacing[2]   ← correct",
]} />

<PullQuote>
  When every component looks correct in isolation but the output is wrong, stop
  checking components — start tracing the data flow between them. Bugs hide at
  the interfaces.

## AI as Force Multiplier

The viewer rebuild ran in parallel with a 10+ major-version Angular framework upgrade. This migration — every file in the codebase, 10 sequential breaking-change steps — was where I integrated AI tooling meaningfully into my engineering workflow for the first time.

The 10+ major-version migration took ~6 weeks. Without AI on mechanical work, significantly longer. The skill wasn't using it — it was knowing precisely where.
